# Design

Add a versioned shared migration for a notification table containing an ID, recipient account ID, report ID, fixed event type, timestamp and read timestamp. Add an index for recipient and descending timestamp. Store no report title, description, reason, notes or free-form content. Atomic lifecycle writes insert recipient rows in the same transaction as report/history changes: new assignee on assignment; old and new assignees on reassignment; current assignee on resolution return; former assignee captured before clearing on reopen. No notification is emitted for failed or rolled-back changes. Historical events are not backfilled.

Use an authenticated active Developer-only endpoint to list at most 50 newest own notifications and an idempotent CSRF-protected operation to mark an owned notification read. Reject or hide other users' notification IDs; do not accept a recipient ID from the client. Return fixed generic messages and notification IDs, timestamps, type and read state, but do not expose report IDs or links for notifications when the recipient is not currently assigned. For assigned recipients, a link must still resolve through existing assignment checks. Polling, deletion, retention policy and delivery outside the app are out of scope. Reload refreshes the list; do not claim real-time delivery.

Use the existing report lock order and commit notifications within the same transaction. Migration must work on a fresh and existing supported schema. Test failure rollback, current/previous assignment, reopening, return, unauthorized list/read and direct report access after reassignment. No protected content is present in the stored notification itself.

## API and storage contract

Table `developer_notifications`: `id uuid` primary key, `recipient_id uuid NOT NULL`, `report_id uuid NOT NULL`, `event_type text NOT NULL` constrained to `ASSIGNED`, `UNASSIGNED`, `RESOLUTION_RETURNED`, or `REOPENED`, `created_at timestamptz NOT NULL`, and nullable `read_at timestamptz`. The returned notification does not include report content. Use a stable ID and a unique event identity sufficient to prevent duplicates for the same recipient, report, report version and type.

`GET /api/developer/notifications` returns `{"items":[{"id":"uuid","type":"ASSIGNED","createdAt":"ISO-8601","read":false,"reportId":"uuid or null"}]}` ordered by timestamp and ID descending, capped at 50. `reportId` is null unless the caller is currently assigned to that report, including for UNASSIGNED and REOPENED events. UI maps enum values to generic fixed labels, and only shows a report link when `reportId` is present. `POST /api/developer/notifications/{id}/read` accepts an empty body, requires CSRF, returns 204 for an owned notification (including already-read), and returns 404 for invalid, missing or unowned IDs. Missing authentication returns 401; wrong role or inactive account is denied by the shared security layer. No API accepts a caller-supplied recipient. All endpoints use no-store.
